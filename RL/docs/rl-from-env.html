環境から入る強化学習

強化学習で自分が書くのは、たいてい環境のほうです。reach_env.py の各行が、なぜそう書かれているのかを1つずつ埋めていきます。

全7章 写経コード 7本 数式は最小限 学習は回しません
序

書くのは環境のほう

PPO のアルゴリズム本体は、たいてい既製品（stable-baselines3 など）を使います。自分が手で書くのは、その相手側 ——環境です。だから強化学習を理解するとは、まずこの2者がやりとりする約束事を理解することだと言い換えられます。

この図に出てくるものが、そのまま reach_env.py の各パーツに対応します。以降の7章は、それぞれファイルの特定の行を出発点にして、その行がなぜそう書かれているのかを埋めていきます。

この本の読み方

各章の頭に、その章が説明する reach_env.py の行を置いてあります。まずその行を見て、「なぜこう書くのか」が言えるか自分に聞いてみてください。言えなければ、その章が埋める場所です。

写経コードは reach_env.py と同じディレクトリに置いて実行します。学習は一度も回しませんので、どれも数秒で終わります（第6章だけ、学習済みモデルがあれば読み込みます）。

第 1 章

ループ ── reset と step

この章が説明する行 def reset(self, *, seed=None, options=None): def step(self, action):

強化学習の環境は、たった2つのメソッドで世界を表現します。reset() が「最初の観測」を出し、step(action) が「行動を受け取って世界を1つ進める」。この2つが全部です。

step() は5つの値を返します。名前を覚えるより、それぞれが誰への手紙かで覚えるほうが早いはずです。

返り値誰への手紙か
observation方策へ。「次にこれを見て決めてください」
reward学習アルゴリズムへ。「いまの一手はこれくらいの値打ちでした」
terminated学習アルゴリズムへ。「この先はもうありません」
truncated学習アルゴリズムへ。「こちらの都合で切りました。先はまだあります」
info人間へ。学習には使われない、デバッグ用の置き場

terminated と truncated の違いは第7章まで持ち越します。ここでは「2つある」とだけ頭に置いてください。

写経 ── ループを手で回す

学習は使いません。でたらめな行動を投げて、環境が何を返すかだけを見ます。

§

式の読み方

この節が説明する記号 P(s′ | s, a) R(s, a) π(a | s) V^π(s) = E[G | s, π]

次の章から式が出てきます。といっても覚えることは多くありません。縦棒の右を「入力」、左を「出力」と読む——この一手で、この本に出てくる式は全部読めます。順に組み立てます。

1. 記号は6つだけ

まず登場人物です。すべて第1章の step() でもう見たものに、名前がついただけです。

記号読み意味reach_env.py での正体
sエスいま方策に見えているもの（観測・状態）_get_obs() の戻り値
aエー方策が出す指令（行動）step(action) の引数
s′エス ダッシュ1ステップ後の観測。′ は「次の」の意味で、微分ではないstep() の戻り値 1つ目
rアールそのステップで貰った点数（報酬）step() の戻り値 2つ目
γガンマ先の報酬をどれだけ軽く見るか（割引率、第5章）PPO の gamma
πパイ観測から行動を決めるもの（方策）model

大文字と小文字も区別があります。R は「報酬を決める規則」、r は「実際に返ってきた数値」。同じく G は1本走らせた実績で、V はその平均の見積もりです（第5章・第6章）。大文字は規則や見積もり、小文字は実際に出た数と思っておくとほぼ合います。

2. 縦棒 | は「〜のとき」

P(A | B) は「B が与えられたとき、A が起きる確率」と読みます。条件付き確率という名前がついていますが、読み方はこの1つだけです。

3. 関数のシグネチャに直す

ここが一番効く読み替えです。縦棒の右は引数、左は返り値。そう思って Python に直すと、式はすべてもう書いたコードそのものになります。

式読み下しPython でいうと誰が書くか
π(a | s) 観測 s のとき、行動 a を選ぶ確率 action = model.predict(obs) PPO（学習する）
P(s′ | s, a) 観測 s で行動 a をしたとき、次が s′ になる確率 obs2, ... = env.step(a) の obs2 自分（環境）
R(s, a) 観測 s で行動 a をしたときに返す報酬 ..., reward, ... = env.step(a) 自分（環境）
Vπ(s) 観測 s から方策 π で動いたときの、リターンの平均 第6章で実際に数える PPO（推定する）

4つとも step() と predict() の言い換えです。どの式が自分の担当かは、縦棒の左を見れば分かります。左が s′ や報酬なら世界の話（＝自分が書く環境）、左が a なら方策の話（＝PPO の担当）です。P と π はここで区別します。

なぜ「確率」で書くのか

同じ s で同じ a をしても結果がばらつく環境があるからです（風が吹く、相手が動く、センサに雑音が乗る）。ばらつくなら行き先は1点では書けないので、分布——つまり確率で書くしかありません。

この本の環境の遷移は pos + 0.05 * a で決定的です。行き先の確率は 1。ですから P(s′ | s, a) は普通の関数だと思って読んで構いません。それでも確率の形で書いておくのは、ばらつく環境も同じ式で扱えるようにするためです。

4. 式を読む3手順

式に出くわしたら、意味を思い出すのではなく、この3つを機械的にやります。

  1. 縦棒の右を全部書き出す。これが「与えられているもの」の全部で、ここに無い情報は使えない。
  2. 右側を固定したとき、左側が1つに決まるか自問する。同じ右側で左側が揺れないか。
  3. 決まらないなら、右側に足りないものがある。足すか、諦めるか、履歴を持たせるかの3択になる。

この手順をこの環境でやると、そのまま次の章になります。R(s, a) の右側は s と a だけ。ところが s = [x, y] にすると、報酬 -dist は今回の目標次第で変わるので、手順2で「決まらない」になります。だから goal_id を s に入れる——それが第2章の goal_conditioned です。

5. E[…] は「平均」

第6章に Vπ(s) = E[G | s, π] が出てきます。E は expectation（期待値）、つまりばらつくものの平均です。手順どおりに読むと「s から π で動く、という前提を与えたときの、リターン G の平均」。第6章では実際に何本も走らせて平均を取り、この式の定義どおりに数えます。式が定義で、写経がその実行という関係になっています。

よくある詰まり

s′ の ′ は微分ではありません。「次の s」というだけの印です。

P と π は役割が逆です。P は世界の振る舞い（環境が決める）、π は方策の振る舞い（学習が決める）。縦棒の左で見分けます。

添字つきの r₀, r₁, r₂ は「0手目の報酬、1手目の報酬、…」。時刻を表しているだけです（第5章）。

第 2 章

観測とマルコフ性

この章が説明する行 def _get_obs(self) -> np.ndarray: if not self.goal_conditioned: return self.pos.copy() z = np.zeros(N_GOALS, dtype=np.float32) z[self.goal_id] = 1.0 return np.concatenate([self.pos, z]).astype(np.float32)

環境を書くとき、いちばん設計判断が要るのが「何を見せるか」です。持っている情報を全部渡す必要はありませんが、足りないと解けなくなります。その境目を決めるのがマルコフ性という条件で、この章の goal_conditioned は、その境目をまたぐスイッチです。

goal_conditioned は何のスイッチか

この環境には的が3つあります（左・右・上）。そしてエピソードごとに、そのうち1つだけが「今回の目標」になります。目標は reset() がランダムに選び、self.goal_id として環境の中に持っています。報酬も、その的との距離で決まります。

つまり環境は目標を知っています。goal_conditioned が決めるのは、その知っている目標を方策にも見せるかどうか、それだけです。学習アルゴリズムの設定でも、報酬の設定でもありません。

環境の中身goal_conditioned = Falsegoal_conditioned = True
方策に渡す観測[x, y][x, y, z0, z1, z2]
観測の次元25
目標 goal_id環境の中にはあるが、見せないone-hot の z にして見せる
的の位置・動き方同じ同じ
報酬の式同じ（goal_id を使う）同じ（goal_id を使う）

変わるのは _get_obs() の戻り値だけです。世界の側は1ミリも変わっていません。方策に開けてある窓の大きさだけが変わります。

なぜ「見せない」と解けなくなるのか

理由はひとつだけです。方策は「観測を受け取って行動を返す関数」だから。関数なので、入力が同じなら出力も同じになります。

エピソードの最初、位置はいつも原点です。だから goal_conditioned=False では、目標が左でも右でも上でも観測は [0. 0.]。方策から見ると3つは区別のつかない同じ場面なので、同じ行動しか返せません。「左へ」を覚えれば右と上で損をし、「右へ」を覚えれば左と上で損をする。損がいちばん小さいのは3つの的の平均あたりへ行くことで、結果としてどの的にも届きません。

これは学習が下手なせいではありません。学習時間を10倍にしても、もっと強いアルゴリズムに替えても変わりません。同じ入力に別々の出力を返す関数は存在しない、というだけの話だからです。

観測に z を足すと、3つの場面は別々の入力になります。入力が違えば出力を変えられる。1つのネットワークが3つの打ち分けを覚えられるようになる——変えたのは環境の引数1つだけです。

マルコフ性 ── 足りているかどうかの基準

「観測が足りている」を厳密に言ったものがマルコフ性です。条件は2行しかありません（記号の読み方は § 式の読み方。| の右が「与えられているもの」、左が「知りたいこと」です）。

P(s′ | s, a)
次に何が起きるかが、いまの観測と行動だけで決まる。過去の履歴を持ち出さなくていい
R(s, a)
もらえる報酬も、いまの観測と行動だけで決まる。観測に映っていない事情で報酬が変わってはいけない

この2行のどちらかが崩れていると、方策は原理的に正しく判断できません。写経で、崩れている様子を目で見ます。

この環境で崩れているのは下の行

位置の更新は pos + 0.05 * a で、goal_id とは無関係です。つまり1行目（遷移）は [x, y] だけでも成り立っています。崩れるのは2行目で、報酬 -dist が観測に映っていない goal_id に依存しているからです。

結果として、まったく同じ観測・同じ行動に、エピソードごとに違う報酬がつきます。この状態を「マルコフでない」と呼びます。「良い状態とは何か」が定まらないので、第6章の価値もここで一緒に壊れます。

写経 ── 観測が状況を区別できるか調べる

●ch2_markov.py
"""第2章: その観測だけで行動を決められるか（マルコフ性）を確かめる。

同じ状況で観測が一致してしまうなら、観測だけでは正しい行動を選べない。
"""

import numpy as np

from reach_env import ReachEnv

for goal_conditioned in (False, True):
    env = ReachEnv(goal_conditioned=goal_conditioned)
    print(f"--- goal_conditioned={goal_conditioned} ---")

    seen = []
    for goal_id, name in enumerate(["left", "right", "up"]):
        obs, _ = env.reset(seed=0, options={"goal_id": goal_id})
        seen.append(obs.copy())
        print(f"  goal={name:<5} obs after reset: {obs}")

    same = all(np.array_equal(seen[0], o) for o in seen)
    print(f"  all three identical: {same}")
    print("  ->", "indistinguishable (not Markov)" if same else "distinguishable (Markov)")
    print()
>出力

  goal=right obs after reset: [0. 0.]
  goal=up    obs after reset: [0. 0.]
  all three identical: True

やっていることは単純で、違う状況を並べて、観測が一致しないかを見るだけです。自分の環境でも同じことができます。「本来なら別々の行動をとるべき2つの場面」を用意して、観測を print して見比べてください。

よくある勘違い

思いがちなこと実際
goal_conditioned は学習アルゴリズムのオプション 環境が観測に何を入れるかのスイッチ。PPO 側のコードは step1_plain.py と step2_goal.py でまったく同じ
z を渡すのは答えを教えるズル 教えているのは「どれを狙うか」であって「どう動くか」ではない。動き方は学習が自分で見つける
見せなくても、学習を長く回せばいつかは解ける 解けない。同じ入力に別々の出力を返す関数は作れないので、原理的に不可能
z は的の座標 ここでは3つのうちどれかを表す one-hot。座標を渡す設計もありうる。何を渡すかは設計判断（第3章）
観測は多いほど良い 足りないと解けないが、要らない次元は学習を遅くする。基準は「その観測だけで正しい行動が決まるか」
ここが効く

目標が3つあるのに観測が [0. 0.] しかないなら、方策は3つの状況を区別できません。学習が下手なのではなく、渡している情報が足りていない。

環境がうまく学習しないとき、真っ先に疑うのはここです。報酬をいじる前に、「その観測だけで、人間なら正しい行動を選べるか」を確かめてください。選べないなら、方策にも選べません。

ちなみに「観測が足りない問題」には名前があります。部分観測マルコフ決定過程（POMDP）です。対処は2つしかありません。足りない情報を観測に足すか、過去の履歴を持たせる（LSTM やフレーム重ねなど）か。目標ベクトル z は前者の一例です。

第 3 章

空間を宣言する

この章が説明する行 self.action_space = spaces.Box(-1.0, 1.0, shape=(2,), dtype=np.float32) self.observation_space = spaces.Box(-np.inf, np.inf, shape=(obs_dim,), ...)

この2行は、環境が外部に対して出す型の宣言です。「行動として何を受け付けるか」「観測として何を返すか」を先に約束しておく。学習アルゴリズムはこれを読んで、ネットワークの入力層と出力層のかたちを決めます。

だから MlpPolicy と書くだけで動くわけです。入力を5次元にするか2次元にするかを、あなたが指定した覚えがないのは、observation_space がそれを伝えているからです。

  • Box ── 連続値。ロボットのトルクや速度指令
  • Discrete(n) ── 離散値。上下左右のような選択肢
  • ほかに MultiDiscrete、Dict などもあります

写経 ── 空間の中身を覗く

第 4 章

報酬 ── 何をしてほしいかだけを書く

この章が説明する行 dist = float(np.linalg.norm(self.pos - TARGETS[self.goal_id])) reward = -dist # 目標に近いほど高い

報酬はスカラー1個です。ベクトルでも辞書でもなく、数字がひとつ。ここに書けるのは「何をしてほしいか」だけで、「どうやってほしいか」は書けません。やり方のほうは学習が見つけます。

設計上の分かれ道は、密か疎かです。

種類書き方性質
密（dense）-dist毎ステップ手がかりが返る。学習は速いが、設計者の想定が濃く入る
疎（sparse）到達で +1やってほしいことだけを正直に書ける。ただし当たるまで何も返らない

写経 ── どれだけ手がかりが返るか測る

"""第4章: 密な報酬とまばらな報酬で、返ってくる手がかりの量を比べる。

第 5 章

リターンと割引

この章が説明する行 # reach_env.py には書かれていない。PPO 側の gamma がこれを決める

報酬は一手ぶんの点数です。方策が最大化したいのは一手ではなく、これから貰う報酬の合計。これをリターンと呼びます。

式の記号は § 式の読み方 のとおりです。r₀ は0手目の報酬、r₁ は1手目の報酬、添字は時刻を表します。

G = r₀ + γr₁ + γ²r₂ + …
いま貰う報酬はそのまま、1手先は γ 倍、2手先は γ² 倍。先の報酬ほど割り引く

γ（ガンマ）は 0 以上 1 以下の数で、どれだけ先まで気にするかのつまみです。0 なら次の一手しか見ない近視眼。1 に近いほど遠い将来まで勘定に入れます。

なぜ割り引くのか。理由は2つあります。終わらないエピソードでも合計が発散しないためと、遠い先の予測ほど当てにならないため。実務では 0.99 が既定値としてよく使われます。

写経 ── gamma で判断が変わる瞬間を見る

●ch5_return.py
"""第5章: リターンと割引率 gamma。

同じ報酬の並びでも、gamma を変えると「どちらが得か」の判断が変わる。
"""

NOW = [1.0] + [0.0] * 9        # いますぐ +1
LATER = [0.0] * 9 + [10.0]     # 9手待って +10


def discounted_return(rewards, gamma: float) -> float:
    """G = r0 + γr1 + γ²r2 + ... を後ろから畳んで計算する。"""
    g = 0.0
    for r in reversed(rewards):
        g = r + gamma * g
    return g


print(f"{'gamma':>6} | {'+1 now':>12} | {'+10 in 9 steps':>14} | pick")
print("-" * 48)
for gamma in (0.0, 0.5, 0.9, 0.95, 0.99, 1.0):
    a = discounted_return(NOW, gamma)
    b = discounted_return(LATER, gamma)
    print(f"{gamma:>6.2f} | {a:>12.4f} | {b:>14.4f} | {'now' if a > b else 'later'}")

print()
print("gamma is the knob for how far ahead you care.")
print("0 looks only at the next step; closer to 1 counts the distant future.")

実装では reversed() で後ろから畳んでいます。素直に γt を毎回計算するより速く、数値的にも安定します。この畳み方は、このあと価値の計算でも同じ形で出てきます。

第 6 章

価値 ── 状態に点数をつける

この章が説明する行 # これも reach_env.py にはない。PPO が内部で推定している量

リターンは1回走ってみないと分かりません。走る前に「この状態から始めたら、だいたいどれくらい貰えるか」を見積もりたい。それが価値です。

Vπ(s) = E[G | s, π]
状態 s から方策 π で動いたときの、リターンの期待値

読み方は § 式の読み方 の手順どおりです。E は期待値＝ばらつくものの平均、縦棒の右の s, π が「与えられているもの」。つまり「s から π で動く、という前提でのリターンの平均」と読みます。

ここで見落としやすいのが、右肩の π です。価値は状態だけでは決まりません。「どの方策で動くか」とセットで初めて決まる量です。同じ状態でも、下手な方策なら価値は低く、上手な方策なら高い。

写経 ── 定義どおりに数える

期待値なので、たくさん試して平均を取れば出ます。これをモンテカルロ推定と呼びます。

●ch6_value.py
"""第6章: 価値を定義どおりに見積もる。

V(s) = その状態から先に貰えるリターンの期待値。
定義そのままに、たくさん試して平均を取る（モンテカルロ推定）。

ppo_goal.zip があれば、学習済み方策の価値とも比べる。
"""

import numpy as np

from reach_env import ReachEnv

GAMMA = 0.99
N_EPISODES = 300
NAMES = ["left", "right", "up"]


def discounted_return(rewards) -> float:
    g = 0.0
    for r in reversed(rewards):
        g = r + GAMMA * g
    return g


def estimate_value(policy, goal_id: int) -> tuple:
    """原点から始めたときのリターンを N 回集めて平均する。"""
    env = ReachEnv(goal_conditioned=True)
    env.action_space.seed(0)
    returns = []
    for ep in range(N_EPISODES):
        obs, _ = env.reset(seed=ep, options={"goal_id": goal_id})
        rewards = []
        for _ in range(env.max_steps):
            obs, r, term, trunc, _ = env.step(policy(obs, env))
            rewards.append(r)
            if term or trunc:
                break
        returns.append(discounted_return(rewards))
    xs = np.array(returns)
    return xs.mean(), xs.std() / np.sqrt(len(xs))


def random_policy(obs, env):
    return env.action_space.sample()


print(f"Monte Carlo estimate of V(origin)   gamma={GAMMA}, {N_EPISODES} episodes")
print()
print(f"{'':10} {'random policy':>16} {'trained policy':>16}")
print("-" * 50)

trained = None
try:
    from stable_baselines3 import PPO

    model = PPO.load("ppo_goal")

    def trained_policy(obs, env):
        action, _ = model.predict(obs, deterministic=True)
        return action

    trained = trained_policy
except Exception:
    pass

for goal_id, name in enumerate(NAMES):
    m, se = estimate_value(random_policy, goal_id)
    left = f"{m:+.1f} ± {se:.1f}"
    if trained is None:
        right = "(no ppo_goal.zip)"
    else:
        tm, tse = estimate_value(trained, goal_id)
        right = f"{tm:+.1f} ± {tse:.1f}"
    print(f"{'z = ' + name:10} {left:>16} {right:>16}")

print()
print("The same state has a different value under a different policy.")
print("Value is not a property of the state; it is the outlook under that policy.")
print()
print("The three z give nearly the same value because the targets are equidistant.")
print("Move the targets off-symmetry and the values split per z.")

まったく同じ原点なのに、価値が -32 と -4.5 に分かれました。状態は1つ、違うのは方策だけです。価値は状態の性質ではなく、その方策で動いたときの見込みだということが、この2列に出ています。

3つの z でほぼ同じ値になっているのは、3つの的が原点から等距離だからです。的の位置を非対称にすれば、z ごとに価値が割れます。

PPO が実際にやっていること

PPO はこの価値を毎回300回走って測ったりはしません。ニューラルネットにこの値を予測させます（value function、critic）。そして「実際に貰ったリターン」と「予測した価値」の差を使って、方策を押す向きを決めます。この差がアドバンテージです。

つまりアドバンテージとは「予想より良かったか、悪かったか」。予想より良かった行動の確率を上げ、悪かった行動の確率を下げる。それが方策の更新です。

"""第7章: terminated と truncated を取り違えると何がずれるか。

本当に終わった(terminated)なら、この先はゼロ。

症状で覚える

取り違えると、方策は「時間切れの直前がやけに良い状態だ」と学習します。ペナルティが続く環境なら、エージェントは終盤で妙に消極的になったり、逆に打ち切りを待つような動きをしたりする。

学習曲線は伸びているのに挙動が変、というときの定番の原因です。max_steps による打ち切りは truncated であって terminated ではありません。

この reach_env.py では terminated は常に False です。到達しても終わらせず、必ず60ステップ走らせている。「近づいて、そこに留まる」まで含めて評価したいからです。到達したら即終了にすると、通り過ぎるだけの方策も高得点になってしまいます。
